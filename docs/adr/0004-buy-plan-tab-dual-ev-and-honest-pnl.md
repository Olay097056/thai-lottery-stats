# จัดชุดซื้อ (Buy Plan): two isolated modes, theoretical EV, and a locked real-money track record

The Buy Plan page answers a different question from the Decision Center: not "what does the system think will come up" but "given a budget of X baht and a risk appetite, where should the money go." It is a new top-level sidebar page, not a Decision Center sub-tab.

Key decisions (grilling session 2026-07-09):

1. **Two modes behind a toggle, never one budget split across both.** แทงรายเลข (per-number betting: 2 ตัวล่าง `bottom2`, 2 ตัวบน `prize1_last2`, 3 ตัวบน `back3`) and ลอตเตอรี่ใบ (government tickets, bought online so exact 6-digit numbers ARE selectable — search ladder เต็ม 6 → ท้าย 3 → ท้าย 2 for sold-out fallback). Cross-world EV conversion was rejected: the two are bought through different channels at different times, and a unified allocator would need an apples-to-apples prize-structure comparison that adds complexity without matching real behavior.
2. **Risk presets control only the tier split** between 2-digit and 3-digit money (เซฟ 80/20, กลาง 50/50, ใจถึง 20/80). Risk never influences which numbers are picked — that stays purely Edge/score-driven. A "risk = number of picks" interpretation was rejected as conflating two meanings in one control.
3. **Theoretical EV is separate from candidate-set Edge.** Show expected payout from the configured prize schedule, stake, and baseline random probability. Show formula Backtest Edge only as a historical hit-rate difference for the formula's full candidate set. Do not add this set-level rate to each number's or ticket's probability, or convert it to baht. Earlier dual-EV UI treated a candidate-set metric as individual probability and is superseded by this correction (2026-10-16).
4. **Sources: Picks (`dcBuildScoreRows` scores) with เลขแนะนำ numbers boosted ×1.5;** ทดลอง formulas participate normally with the badge shown (per ADR-0003). In ใบ mode the full-6-digit list = I1/I2/J2 pool6 candidates + `predict_prize1_ultimate` + **Mix — included as a labeled *source*, never as a formula group** (it is built from the other groups; counting it in any "distinct groups agree" logic would double-count its parents, per the Mix glossary entry).
5. **Allocation within a tier is proportional to score** (not equal-weight — otherwise Edge only picks *who*, not *how much*), min 20฿/number, rounded to 10฿, max 10 numbers per tier, rounding remainder to rank 1. Numbers allocated below the minimum are dropped and their money redistributed, so pick-count scales with budget naturally.
6. **Payouts and stakes are user config, frozen into each saved record.** Defaults from the owner's real bookie: 2 ตัว ×95, 3 ตัวตรง ×950 (both exactly −5%/baht theoretical), ticket price 80฿, min 20฿ / round 10฿ — all editable in a settings flyout, persisted in localStorage. Editing config later must never retroactively change saved plans' recorded P/L.
7. **Saving is a manual button and the record locks on save.** Unlike the Decision Center's auto-snapshot (which records the *system's* opinion every load to prevent hindsight bias), a buy plan records the *user's* decision — auto-saving exploratory budget-fiddling would drown the history. Before save, rows are fully editable (change stakes, delete, add hand-typed numbers) so the record matches money actually spent; hand-touched rows carry a "แก้เอง" label so system-pure P/L remains separable from human-adjusted P/L. After save: delete-whole-plan only, no edits — hindsight editing breaks the honesty of the cumulative ledger.
8. **Resolution pays in baht, not just Hit/Miss.** On draw publish, each plan resolves per-number (hit = stake × payout) and per-plan (net vs total spent), with an all-time cumulative ledger ("bought N plans, spent X, returned Y, net −Z") shown against the random-play expectation. ใบ mode resolves against the full government prize table (draw cache already holds all prizes).
9. **The existing ไม่รู้ซื้ออะไรดี (Mix) page keeps its budget-cuts feature untouched** and gains a "จัดชุดซื้อจากเลขชุดนี้ →" button that pre-fills the Buy Plan page with Mix as source. Consolidating/removing budget cuts is deliberately out of scope for this arc.
10. **An unchanged purchase record is saved once.** Identity is target date, purchase mode, applicable payout rate, and aggregated wager rows/amounts (including ticket quantity). Budget, risk, rank, and recommendation-source metadata do not make the same purchase distinct. The saved button becomes disabled with an explanation until the user changes actual wagers, target, or payout configuration; an empty plan is also not saveable. If the same draw's purchased amounts need to be recorded together, adjust the stake or ticket quantity before saving. This prevents accidental duplicate ledger totals without changing the immutable saved-record schema.

## Consequences

- The page is client-side only, following the Decision Center pattern: no new backend endpoints; it re-uses data the SPA already fetches (formula batch, เลขแนะนำ, prize1 predictions, prize history).
- The cumulative baht ledger is the project's most honest metric to date — it can and usually will show a growing loss. That is the feature working as designed, not a bug.
- Per-number betting at ×95/×950 is off-book gambling; the page is a personal calculator/ledger for the owner, with payout rates kept configurable precisely because they are dealer-specific.

## Revision — 2026-10-16

The former secondary "adjusted EV" used rolling candidate-set Edge as if it were each individual number's probability. The Edge baseline depends on the size of the formula's candidate set, so this did not establish a calibrated probability for a number or ticket. Buy Plan labels each per-number historical signal `Edge ชุดสูตร` and explains that it is the highest candidate-set Edge among formulas supporting that number, measured against each formula's random baseline in percentage points. The visible note explicitly separates that signal from individual odds and monetary EV; ticket mode has no per-number Edge note. Monetary EV uses only configured payout and the applicable random baseline. Legacy `adjusted` and `warning` fields remain in saved/in-memory data for compatibility, with `adjusted` mirroring theory and `warning` false. Ranking, allocation, endpoints, and saved-plan schema are unchanged.

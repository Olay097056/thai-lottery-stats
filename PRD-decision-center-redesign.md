# PRD: Decision Center (สรุปงวดนี้) consolidation + track record

## Problem Statement

As the person using the "สรุปงวดนี้" (Decision Center) tab to decide which numbers to actually play, I've grown the page to 10 sections over several phases, and it's now working against me: the same Picks show up rendered three different ways (a hero summary, a full "Final Confidence Score" list, and a standalone "หน้า 3 เด่น" card), a "Next Actions" block gives static advice that never reflects the actual data, and — most importantly — the page has no memory of whether its own past recommendations were right. I have no way to look at this page and judge "is this thing actually worth trusting," because nothing on it tracks outcomes over time.

## Solution

Consolidate the duplicated Pick displays into a single ranked Hero/Confidence board (folding in the standalone 3-digit card and the separate detailed Prize1/2-digit/cross-category-support cards), delete the static Next Actions block, and add an Edge badge to each Pick so its strongest supporting formula's backtest performance is visible inline. Replace the manual "บันทึก Snapshot" button with an automatic snapshot taken every page load, and merge the existing Snapshot list with a new Track Record view that marks each past snapshot's Picks as Hit / Miss / Pending once (or until) the target draw resolves. Add a Hit-rate trend chart (Chart.js, consistent with the existing Backtest page) summarizing accuracy over the last 20 resolved draws, and move it near the top of the page — right after the Hero board — so credibility signal is visible before the detail sections.

## User Stories

1. As a dashboard user, I want the top pick number, the full ranked Pick list, the detailed Prize1 cards, the 2-ตัวล่าง cards, and the cross-category support numbers all shown in one consolidated Hero board, so that I don't see the same numbers repeated in three different card styles as I scroll.
2. As a dashboard user, I want the standalone "หน้า 3 เด่น" card removed since its numbers are already in the Hero board's 3-digit row, so that the page doesn't repeat identical data.
3. As a dashboard user, I want the "Next Actions" block removed entirely, so that the page doesn't show static advice text that never reflects what the data actually says.
4. As a dashboard user, I want each Pick in the consolidated list to show an Edge badge (e.g. "482 · edge +12.3%") drawn from its highest-weight supporting formula's backtest Edge, so that I can judge a Pick's credibility without opening the separate formula-match detail card.
5. As a dashboard user, I want "Predict × สูตรคำนวณ ตรงกัน" kept as its own detail card (not merged into the Hero board), since the Hero board's formula-highlights section is only a 3-item teaser and this card is the full detail view, so that I can still drill in without losing the summary/detail distinction.
6. As a dashboard user, I want the page to automatically save a snapshot (target date, mode, Picks with scores) every time I load the สรุปงวดนี้ tab, so that my track record is never incomplete just because I forgot to click a save button.
7. As a dashboard user, I want the manual "บันทึก Snapshot" button removed, since auto-save already captures the same information on every load, so that I don't have a redundant control that adds no new data.
8. As a dashboard user, I want auto-saved snapshots capped to the most recent 60, so that local storage doesn't grow unbounded.
9. As a dashboard user, I want the existing Snapshot list and the new Track Record merged into a single card, so that I see "what was recommended" and "was it right" together instead of switching between two separate lists built from the same underlying snapshots.
10. As a dashboard user, I want each snapshot row to show a per-Pick Hit/Miss status once the target draw's result is known, so that I can see which specific numbers from that round actually came in.
11. As a dashboard user, I want a 6-digit Pick counted as a Hit only on an exact รางวัลที่ 1 match, so that the bar for a 6-digit hit matches the mathematical reality that this is a 1-in-a-million-class outcome.
12. As a dashboard user, I want a 3-digit Pick counted as a Hit if it matches any of the period's five 3-digit result slots (3 ตัวบน, 3 ตัวหน้า ×2, 3 ตัวล่าง ×2), so that the hit definition matches the existing Backtest page's own hit-check convention rather than inventing a stricter one.
13. As a dashboard user, I want a 2-digit Pick counted as a Hit only on an exact 2 ตัวล่าง match, so that the definition is unambiguous for the one 2-digit prize category that exists.
14. As a dashboard user, I want snapshots whose target draw hasn't happened yet marked "รอผล" (Pending) rather than hidden or scored as a miss, so that the list doesn't silently change row count as draws resolve and so that I can see what predictions are still outstanding.
15. As a dashboard user, I want Pending snapshots excluded from hit-rate statistics until they resolve, so that the accuracy numbers aren't distorted by outcomes that don't exist yet.
16. As a dashboard user, I want a hit-rate trend chart showing the last 20 resolved (non-Pending) snapshots as a line chart with a 5-round rolling average, so that I can see whether the system is getting more or less accurate over time rather than judging it off any single round.
17. As a dashboard user, I want the trend chart built with Chart.js, matching the library already used for the Backtest page's lift chart, so that the codebase doesn't gain a second charting dependency for the same kind of visualization.
18. As a dashboard user, I want the Track Record + trend chart section placed directly after the Hero board (before the on-demand Backtest button, Data Health, formula-match, secondary-signal, and risk-cutting cards), so that I see the system's real-world credibility before the supporting detail sections.
19. As a dashboard user, I want the rest of the page's existing sections (on-demand Backtest panel, Data Health, Predict × สูตรคำนวณ ตรงกัน, สัญญาณจากรางวัลรอง, ตัดเลขเสี่ยง) to keep their current behavior and relative order below the new Track Record section, so that this change doesn't disturb functionality outside its stated scope.

## Implementation Decisions

- **Consolidation target:** `dcLottoSummaryBoard` (hero board) absorbs the content currently duplicated across the Final Confidence Score card (`dcScoreHtml`/`dcBuildScoreRows` output), the standalone "หน้า 3 เด่น" card, and the detailed Prize1/2-ตัวล่าง/เลขหนุนข้ามหมวด cards inside the `dc-hero` block in `loadDecisionCenter`. The chip-only versions of Prize1/2-ตัวล่าง in the old hero board are replaced by the more detailed score-annotated versions (`predDetailHtml`-based), not the other way around.
- **Edge badge:** computed per Pick from the existing `formulaWeight`/backtest-edge data already assembled in `dcBuildScoreRows` (via the `btRows`/`btMap` join) — surfaced as a new rendered field on each Pick row rather than a new score input. Use the edge value from the Pick's highest-weight supporting formula.
- **Next Actions removal / หน้า 3 เด่น removal:** delete the corresponding markup blocks and any now-orphaned rendering functions once nothing references them.
- **Auto-snapshot:** `loadDecisionCenter` takes over what `dcSaveSnapshot` currently does (write to the `lottery_dc_snapshots` localStorage key), firing on every successful load rather than only on button click. The manual button and its handler are removed. Cap remains a rolling window, raised from 20 to 60 entries (one entry per page load, so the cap now needs to absorb repeat loads for the same undecided round, not just one save per round).
- **Snapshot dedup on save:** preserve the existing behavior of replacing any prior entry for the same target date (`list.filter(x=>x.date!==next)`) so repeated loads for the same undecided round don't create duplicate rows — the auto-saved entry for a date is always the most recent computation for it.
- **Hit-check function:** a single shared function takes a Pick's number and the actual draw-result row for its target date, and returns `hit` / `miss` / `pending` (pending when no result row exists yet for that date). Digit-length branches: 6-digit → exact `prize1` match; 3-digit → membership in the same five-slot set (`top3`, `front3_1`, `front3_2`, `back3_1`, `back3_2`) already built by the existing `dcBtActual3` helper used in `dcRunDecisionBacktest`; 2-digit → exact `bottom2` match. Reuse `dcBtActual3` rather than re-deriving the five-slot set.
- **Actual-result lookup for past snapshots:** resolve each snapshot's target date against history data already available via the existing `history`/`prize-history` API calls this page already makes — no new endpoint.
- **Merged Snapshot + Track Record card:** extends the existing snapshot list rendering (`dcSnapshotHtml`) to annotate each listed Pick with its Hit/Miss/Pending status, replacing the separate track-record list that would otherwise exist. Existing per-snapshot actions ("โหลดงวดนี้", "ลบ") are kept.
- **Hit-rate trend chart:** a `<canvas>` rendered via Chart.js as a line chart, data = per-round hit rate (% of that round's Picks that were Hits) for the last 20 resolved (non-Pending) snapshots, plus a second series or transform for the 5-round rolling average. Lives in its own card, immediately below the merged Snapshot + Track Record card and above the on-demand Backtest button panel.
- **Section order** (top to bottom) for the "สรุปงวดนี้" tab panel after this change: (1) consolidated Hero/Confidence board, (2) Snapshot + Track Record card, (3) Hit-rate trend chart, (4) on-demand "Backtest เลขเด่นชุดนี้" panel, (5) Data Health, (6) Predict × สูตรคำนวณ ตรงกัน, (7) สัญญาณจากรางวัลรอง, (8) ตัดเลขเสี่ยง.
- **No backend changes.** Everything (Edge lookup, auto-snapshot, hit-checking, trend chart) is computable from data this page already fetches (`summary`, `predict/all`, `prize-history`, `history`) plus client-side localStorage — no new API endpoint, no new Python module.

## Testing Decisions

- Good tests here check the externally observable outcome (rendered DOM content, localStorage contents, computed hit/miss/pending classification) rather than internal call sequencing.
- New standalone fixture-based test script under `scripts/` (following this project's established pattern — no pytest/test framework installed, plain assertion scripts with synthetic fixtures, same convention as `scripts/test_imperial_formula.js` and `scripts/test_pool_field_rename.js`) for the shared hit-check function: fixed synthetic Picks of each digit length against fixed synthetic actual-result rows, asserting `hit`/`miss`/`pending` for each documented case (exact 6-digit match/non-match, 3-digit match against each of the five slots individually, 3-digit non-match, exact/non-exact 2-digit match, and a target date with no result row yet → pending).
- Regression check that auto-snapshot dedup-by-date behavior is unchanged (a second load for the same undecided target date replaces, not duplicates, the prior localStorage entry) — synthetic-fixture assertion, same style as the pool-field-rename regression test from the Group I work.
- Manual browser verification (per this project's established workflow, since there's no automated UI test harness): load "สรุปงวดนี้" and confirm the consolidated Hero board renders once (no duplicate Pick lists elsewhere on the page), confirm "หน้า 3 เด่น" and "Next Actions" no longer appear anywhere, confirm the manual snapshot button is gone, confirm an Edge badge appears on Picks that have a supporting formula with backtest data, confirm the merged Snapshot + Track Record card shows Hit/Miss/Pending correctly for at least one already-resolved past round and the current (unresolved) round, and confirm the trend chart renders without console errors.
- Prior art: `scripts/test_imperial_formula.js`, `scripts/test_codexpool_coeffs.js`, `scripts/test_pool_field_rename.js` for the fixture-script pattern; the FABLE-removal and Group I PRDs' "Testing Decisions" sections for the manual-browser-verification pattern this project relies on in place of automated UI tests.

## Out of Scope

- Any change to the on-demand "Backtest เลขเด่นชุดนี้" panel's own computation (`dcRunDecisionBacktest`) beyond its position on the page — its logic is untouched.
- Any change to Data Health, "Predict × สูตรคำนวณ ตรงกัน", "สัญญาณจากรางวัลรอง", or "ตัดเลขเสี่ยง" beyond their new position below the Track Record section — content and computation untouched.
- A per-digit-length-category breakdown of Hits (e.g. distinguishing "hit 3 ตัวบน" from "hit 3 ตัวหลัง") for Track Record — explicitly rejected in favor of the single coarse Hit/Miss/Pending status, matching the existing Backtest page's own convention.
- A trend view of a specific recurring number's score across multiple rounds it happens to reappear in — considered and rejected as low-value, since Picks rotate every round and this would have frequent data gaps.
- Moving snapshot/track-record storage to the backend (a persisted history endpoint/table) — rejected because this dashboard is used from a single browser/machine; localStorage auto-save fully solves the stated problem (forgetting to click save) without the added surface area of a new backend store.
- Any change to formula groups A–I themselves, or to the Backtest page.
- Mobile/responsive layout work — this project is explicitly desktop-first per existing project decisions.

## Further Notes

- This PRD consolidates three closely related concerns (de-duplication, an Edge-visibility addition, and a new track-record/trend feature) into one unit because all three touch the same `loadDecisionCenter` rendering pipeline and the same underlying `scored`/snapshot data — splitting them would mean re-touching the same functions in three separate passes for no isolation benefit.
- Recommended execution: Sonnet 5, high effort. Reasoning: no new backend surface and every data source already exists, but the change touches a large, already-dense rendering function (`loadDecisionCenter` and its helpers in `static/app.js`) across markup, scoring, snapshot lifecycle, and a new chart — real regression risk from touching that much of one file in one pass argues for high rather than medium effort.
- No issue tracker is configured for this project (no GitHub remote, no external tracker found) — this PRD is filed as a local `PRD-*.md` file at the project root, following the same convention already used by `PRD-fable-promotion-gate.md`, `PRD-formula-group-f-tuning.md`, and `PRD-replace-fable-with-imperial-formulas.md`. If a tracker is set up later via `/setup-matt-pocock-skills`, this file can be filed into it retroactively.
- Hard rules from `DEVELOPMENT_PLAN.md` continue to apply: no backtest-distorting logic (the Hit-rate trend must only reflect genuinely resolved outcomes — Pending exclusion exists specifically to protect this), lottery numbers stay strings, `CHANGELOG.md` gets updated after this lands per existing project convention.

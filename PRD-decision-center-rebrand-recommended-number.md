# PRD: Decision Center (สรุปงวดนี้) rebrand + เลขแนะนำ (Recommended Number)

## Problem Statement

As the person using the "สรุปงวดนี้" (Decision Center) tab to decide which numbers to actually play, I currently see one blended signal per number — the Final Confidence Score, which mixes Predict output, formula matches, and secondary-prize signals together. What I don't have is a direct answer to a much simpler question I actually ask myself every round: "did several genuinely different calculation methods independently land on the same number?" That's a stronger, more legible trust signal than any single blended score, but right now it doesn't exist anywhere on the page — I'd have to manually scan the formula-match detail card myself to spot it. On top of that, the page's current visual design has been iterated through several feature passes and needs a real rebrand rather than another bolt-on.

## Solution

Rebrand the "สรุปงวดนี้" tab with a new layout and component set (same app-wide macOS-dark/gold theme, not a new palette), led by a new **เลขแนะนำ (Recommended Number)** section: for each field type (`bottom2`, `bottom2_unit`, `top3`, `front3`, `back3`, `back3exact`, `prize1_last2`, `prize1_last4_digits`, `pool6`), surface the top-ranked number that 2 or more *different top-level formula groups* (A–I) independently produced, ranked by number of agreeing groups then combined Edge, with a per-field-type empty state when no such number exists this round. เลขแนะนำ is tracked in the same Track Record mechanism as Picks (Auto-snapshot, Hit/Miss/Pending, Hit-rate trend) with its own Edge computed against its own baseline — never presented as inherently trustworthy just because it converges. Four supporting features ship alongside it: an explainer showing which groups agreed on each เลขแนะนำ, a hit-rate trend chart specific to เลขแนะนำ, a comparison strip against the current #1 Pick, and a field-type coverage badge. The current เลขแนะนำ page is preserved byte-for-byte behind a new 4th sub-tab, "(OLD VER)", so nothing that currently exists is lost.

## User Stories

1. As a dashboard user, I want a new "เลขแนะนำ" section at the top of the rebranded สรุปงวดนี้ tab, so that the strongest, most legible trust signal (cross-formula agreement) is the first thing I see.
2. As a dashboard user, I want เลขแนะนำ computed separately from Pick/Final Confidence Score, so that I can see both "the overall best-blended number" and "the number multiple independent methods agree on" even when they point at different numbers.
3. As a dashboard user, I want เลขแนะนำ agreement to require an exact field-type match (not just equal digit length), so that a `front3` guess and a `back3exact` guess of the same digits are never conflated as "the same recommendation" when they're actually different prize slots.
4. As a dashboard user, I want เลขแนะนำ agreement to require 2+ *different top-level formula groups* (not sub-formulas of the same group), so that two variants of the same underlying method (e.g. จักรพรรดิ + จักรพรรดิทองคำ) agreeing with themselves is never mistaken for independent confirmation.
5. As a dashboard user, I want to see, understand, and accept that `pool6`, `back3`, `prize1_last4_digits`, and `bottom2_unit` structurally can never produce a เลขแนะนำ (each has exactly one producing group today), so that the section doesn't pretend these categories have a convergence signal they mathematically cannot have.
6. As a dashboard user, I want the page to show one เลขแนะนำ per eligible field type (top-ranked by number of agreeing groups, tie-broken by combined Edge of the agreeing groups), so that the section stays scannable rather than listing every number that happens to qualify.
7. As a dashboard user, I want to optionally expand a field type's เลขแนะนำ row to see any other numbers that also qualified this round, so that I'm not hiding real signal just to keep the default view clean.
8. As a dashboard user, I want a field type with no qualifying number this round to show a plain empty state ("ยังไม่มีสูตรเห็นตรงกันในงวดนี้"), so that the absence of convergence is honestly represented instead of backfilled with a lower-confidence substitute.
9. As a dashboard user, I want each เลขแนะนำ to show which specific top-level groups agreed on it ("ทำไมถึงแนะนำ"), so that I can judge the recommendation myself instead of trusting a black box.
10. As a dashboard user, I want เลขแนะนำ tracked in the same Auto-snapshot / Track Record mechanism as Picks, so that its accuracy claim is held to the same standard as everything else on this page.
11. As a dashboard user, I want เลขแนะนำ's own Edge computed against its own baseline (accounting for how many groups produce each field type, since e.g. `bottom2` has 6 possible producing groups versus `front3`'s 2), so that a high เลขแนะนำ hit rate on `bottom2` isn't mistaken for the same statistical significance as one on `front3`.
12. As a dashboard user, I want a hit-rate trend chart specific to เลขแนะนำ (separate line/chart from the existing Pick hit-rate trend), so that I can directly judge whether เลขแนะนำ is actually more accurate than an ordinary Pick over time, not just assume it.
13. As a dashboard user, I want a comparison strip showing this round's เลขแนะนำ against the current #1 Pick side by side, so that I can immediately see whether the two signals reinforce each other or point at different numbers.
14. As a dashboard user, I want a small badge showing how many of the 9 field types have a เลขแนะนำ this round (e.g. "3/6 มีเลขแนะนำ" — using the count of structurally-eligible field types as the denominator, not all 9), so that I can gauge how much convergence signal exists this round at a glance without reading every row.
15. As a dashboard user, I want the rebranded สรุปงวดนี้ tab to use new layout and component styling, so that it feels like a genuine visual refresh rather than another feature bolted onto the existing design.
16. As a dashboard user, I want the rebrand to keep the app-wide macOS-dark/gold theme (`--bg`, `--surface`, `--gold`, `--accent`, etc.) rather than introduce a separate palette for this one tab, so that it doesn't look like it fell out of the rest of the app.
17. As a dashboard user, I want the current (pre-rebrand) สรุปงวดนี้ page preserved exactly as it is today, moved under a new 4th sub-tab labeled "(OLD VER)" alongside ทำนาย / สูตรคำนวณ / สรุปงวดนี้, so that I can still reach the old version if I ever need to compare or fall back.
18. As a dashboard user, I want "(OLD VER)" to be a straight copy — same markup, same `loadDecisionCenter`-equivalent logic, same behavior — with no changes at all, so that rebrand work on the new tab carries zero risk of also breaking the old one.
19. As a dashboard user, I want the new สรุปงวดนี้ tab to become the default sub-tab (replacing the current one's position), so that I land on the rebranded experience without extra navigation.
20. As a dashboard developer, I want เลขแนะนำ computed by a new, separately-testable pure function (not a reuse or modification of the existing `dcConsensusCandidates`, whose same-length field-type merging conflicts with this feature's stricter exact-field-type rule), so that the two behaviors don't silently interfere with each other.
21. As a dashboard developer, I want this feature to require no backend changes, so that it ships purely as client-side additions to `static/index.html`, `static/app.css`, and `static/app.js` (plus the new pure function, wherever it's placed alongside or near `dcConsensusCandidates`).

## Implementation Decisions

- **New pure function for the core computation** (naming placeholder: `dcRecommendedNumbers`): takes the same per-formula-group raw results already assembled before `dcBuildScoreRows` runs (each result tagged with its top-level group letter and `field`), and returns, per field type, the ranked list of `{number, groups: [...], combinedEdge}` where `groups.length >= 2` and all `groups` are distinct top-level letters (A–I; F/Codex counted as one group despite its internal `X`-prefixed sub-formulas). This is a new function, not a modification of the existing `dcConsensusCandidates` (which merges `top3`/`front3`/`back3`/`back3exact` together for a different, already-shipped purpose — the "หลักเด่น" strips — and must be left untouched).
- **Group identity for convergence purposes:** derived from each formula result's existing name-based group badge mapping (the `_GRP` map keyed by `name[0]`, with the existing "F · Codex" special case for `X`-prefixed formulas) — same source of truth already used for badge rendering, not a new classification.
- **Structural exclusions:** `pool6`, `back3`, `prize1_last4_digits`, and `bottom2_unit` are single-producer field types today and will simply never appear in `dcRecommendedNumbers`'s output — no special-case code needed to exclude them, since the `groups.length >= 2` / distinct-group check already makes this impossible. If a future formula group starts producing one of these field types, it becomes eligible automatically.
- **Ranking:** within a field type, sort by `groups.length` descending, tie-break by `combinedEdge` (sum or average of the agreeing groups' backtest Edge — reuse the same Edge lookup already wired into `dcBuildScoreRows`'s `btRows`/`btMap` join) descending. Render the #1 result; the rest of that field type's qualifying numbers are available behind an expand/toggle affordance in the row.
- **Empty state:** a field type with zero qualifying numbers renders a distinct empty-state row/message, not a fallback to a lower-confidence number.
- **Explainer ("ทำไมถึงแนะนำ"):** renders the `groups` array from each เลขแนะนำ result directly (e.g. "A + D เห็นตรงกัน") — no new data needed beyond what `dcRecommendedNumbers` already returns.
- **Coverage badge:** count of field types with `groups.length >= 2` this round, over the count of *structurally eligible* field types (i.e. field types with 2+ historical producing groups — `bottom2`, `top3`, `front3`, `back3exact`, `prize1_last2` — not all 9), so the denominator doesn't unfairly include field types that can mathematically never qualify.
- **Comparison strip:** renders this round's #1-ranked เลขแนะนำ (across all field types, or per the most prominent field type — same ranking rule) next to the existing #1 Pick from `dcBuildScoreRows`'s output, both already computed on page load; no new data fetch.
- **Track Record integration:** เลขแนะนำ per round is captured in the same auto-snapshot write `loadDecisionCenter` already performs (same `lottery_dc_snapshots` localStorage key, extended with a เลขแนะนำ field per snapshot), and hit-checked with the same shared hit-check function (`hit`/`miss`/`pending` by digit length) already built for Pick tracking — reused, not duplicated.
- **เลขแนะนำ's own Edge/baseline:** a new baseline definition per field type reflecting the probability that 2+ of that field type's known producing-group count would coincidentally agree (distinct from the existing per-formula Edge baseline, which is about one formula's accuracy against random chance, not about coincidental cross-formula agreement). Edge = actual เลขแนะนำ hit rate − this new baseline. Rendered as its own metric, never merged into or displayed as the same number as a formula's individual Edge.
- **Hit-rate trend chart for เลขแนะนำ:** a second Chart.js line chart (or a second series on a chart with a toggle — implementer's choice at issue-split time), separate from the existing Pick hit-rate trend chart, computed from the same resolved-snapshot history, same 5-round rolling average / last-20-resolved convention as the existing trend chart.
- **Tab structure:** add a 4th sub-tab, "(OLD VER)", to the existing `switchPredTab()` mechanism (ทำนาย / สูตรคำนวณ / สรุปงวดนี้ / (OLD VER)). "(OLD VER)" gets its own div id and its own copy of the current `loadDecisionCenter` (renamed, e.g. `loadDecisionCenterOld`) and current markup, byte-for-byte, wired to the current tab's existing behavior with zero modification. The rebranded page takes over the "สรุปงวดนี้" tab's existing id/position and becomes the new default.
- **Visual rebrand:** new layout/component styling for the "สรุปงวดนี้" tab only, built from the existing `:root` CSS variables in `static/app.css` (`--bg`, `--surface`, `--gold`, `--accent`, etc.) — no new palette. Existing hardcoded non-tokenized colors specific to the old `.dc-*` classes (e.g. `.dc-score`'s `#8ee9ba`, `.dc-meter-fill`'s gradient) are not required to be preserved, since this is a genuine rebrand of that markup, but any new colors introduced should be tokenized (added to `:root` if reused, not hardcoded) rather than repeating the old file's inconsistency.
- **No backend changes.** Everything is computed client-side from formula results and data this page already fetches.

## Testing Decisions

- Good tests here check externally observable output (the shape of `dcRecommendedNumbers`'s return value, rendered DOM content for the เลขแนะนำ section, localStorage snapshot contents, computed hit/miss/pending for เลขแนะนำ) rather than internal call sequencing.
- New standalone fixture-based test script under `scripts/` (following this project's established pattern — plain assertion scripts with synthetic fixtures, same convention as `scripts/test_decision_track_record.js`, `scripts/test_imperial_formula.js`, `scripts/test_pool_field_rename.js`) for `dcRecommendedNumbers`: synthetic formula results across multiple groups and field types, asserting — (a) 2 different groups agreeing on the same field type + number produces a เลขแนะนำ; (b) 2 sub-formulas of the *same* group agreeing does NOT; (c) 2 different groups agreeing on the same digits but different field types (e.g. `front3` vs `back3exact`) does NOT; (d) ranking order when multiple numbers qualify (more groups wins, then combined Edge); (e) `pool6`/`back3`/`prize1_last4_digits`/`bottom2_unit` fixtures never produce a result regardless of input, proving the structural exclusion holds.
- Extend the existing Track Record fixture test (`scripts/test_decision_track_record.js`) with เลขแนะนำ hit/miss/pending cases, reusing the same shared hit-check function fixtures already established there rather than writing new hit-logic tests.
- Regression check that the existing `dcConsensusCandidates` output and the "หลักเด่น" strips it feeds are byte-for-byte unchanged by this work (since a new, separate function is used instead of modifying it).
- Manual browser verification (per this project's established workflow — no automated UI test harness): load the rebranded "สรุปงวดนี้" tab and confirm the เลขแนะนำ section renders with correct per-field-type results and empty states; confirm the explainer, coverage badge, comparison strip, and เลขแนะนำ-specific trend chart all render without console errors; switch to the new "(OLD VER)" tab and confirm it renders identically to today's current เลขแนะนำ page with no behavior differences; confirm auto-snapshot now includes เลขแนะนำ data and that at least one past resolved round shows a correct Hit/Miss for it.
- Prior art: `scripts/test_decision_track_record.js` for the Track Record fixture pattern; `scripts/test_imperial_formula.js` and `scripts/test_pool_field_rename.js` for the general fixture-script convention; the Decision Center redesign PRD's Testing Decisions section for the manual-browser-verification convention this project relies on in place of automated UI tests.

## Out of Scope

- Any change to `dcConsensusCandidates` or the "หลักเด่น" (3 หลักเด่น / 2 ตัวเด่น) strips it feeds — left completely untouched; เลขแนะนำ is computed by a new, separate function.
- Any change to the Final Confidence Score computation (`dcBuildScoreRows`) itself — เลขแนะนำ is displayed alongside Picks, not blended into their score.
- Allowing sub-formulas within the same top-level group (e.g. I1 + I2, or D1 + D4) to count as independent agreement — explicitly rejected; only distinct top-level groups (A–I) count.
- Merging same-digit-length field types (e.g. treating `front3`/`back3`/`back3exact`/`top3` as interchangeable) for เลขแนะนำ purposes — explicitly rejected, unlike `dcConsensusCandidates`'s existing behavior; เลขแนะนำ requires an exact field-type match.
- Backfilling a field type's empty เลขแนะนำ state with a lower-confidence substitute (e.g. the top single-group candidate) — explicitly rejected in favor of an honest empty state.
- A separate visual identity/palette for the rebranded tab distinct from the rest of the app — rejected; rebrand reuses existing `:root` tokens.
- Any modification to "(OLD VER)"'s markup or behavior beyond the copy/rename needed to give it its own tab — it must remain functionally identical to today's current page.
- A push notification / alert system for เลขแนะนำ — not requested, out of scope for this PRD.
- A copy-to-clipboard quick-buy affordance — considered during scoping but not selected as one of the four supporting features; can be proposed separately later if wanted.
- Mobile/responsive layout work — this project is explicitly desktop-first per existing project decisions.
- Any backend/API changes — everything here is client-side.
